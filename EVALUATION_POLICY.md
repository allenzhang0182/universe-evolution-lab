## 1. Purpose

This policy defines how AI-assisted development work is evaluated and verified.

AI-generated code, documentation, configuration, or task output **must not** be
considered verified **solely because the AI claims it is complete**. A
completion report or a self-assessment from an AI tool is not proof of
correctness.

Verification requires independent evidence: exact checks where available,
human review where required, and AI judge output only as supporting evidence.

---

## 2. Evaluation Priority

When evaluating AI-assisted output, apply the following priority:

1. **Exact evaluation** whenever available
2. **Human review** where required
3. **AI judge** as supporting evidence

Only a **required deterministic gate** blocks an AI judge from overriding a
failure. When a required deterministic check fails, an AI judge **cannot**
override that failure, and a final PASS is not permitted until the failure is
resolved or an explicit review has confirmed that the check is invalid or not
applicable for this task.

Optional / diagnostic deterministic checks must not automatically become
universal blocking gates; they only gate a result when the task defines them as
required.

---

## 3. Functional Correctness

For code tasks, functional correctness is the core metric. Verify:

- whether the change satisfies the acceptance criteria
- whether tests pass
- whether the build passes (where applicable)
- whether existing functionality is not broken
- whether the diff is limited to the allowed scope
- whether there are any security, permission, or data risks

If functional correctness cannot be proven, the task is not complete.

---

## 4. Exact Evaluation

Exact evaluation includes, but is not limited to:

- unit tests
- integration tests
- build
- lint
- type checking
- syntax checks
- deterministic validation scripts
- static checks
- git diff / allowed-scope checks
- file existence / permissions checks
- negative regression tests
- false-positive regression tests

Any problem that can be detected deterministically **should not rely primarily
on an AI judge**. Prefer a reproducible check over a probabilistic opinion.

---

## 5. Completion Report Policy

An AI completion report, a tool summary, or an agent self-assessment is
**execution evidence only**; it is **not** independent verification.

Key claims made in a completion report should be verified by independent
commands or by a review where possible. For example, "tests pass" should be
backed by an actual test run result, not just by the AI stating that it ran
them.

---

## 6. Known-Failure Regression Policy

A real failure mode that has occurred and can be deterministically reproduced
should be considered for conversion into an automated regression check.

Typical flow:

```
real failure
→ define invariant
→ deterministic check
→ negative regression test
→ false-positive check when applicable
```

If a failure can be caught by an exact check, do not rely on future human
discovery or on an AI judge noticing it again.

---

## 7. AI Judge Policy

An AI judge may provide **supporting evidence only**. It is never the sole
passing condition.

When an AI judge is used, record at minimum:

- Task ID / PR ID
- Risk Level
- Judge Model
- Judge Model Version (if available)
- Judge Prompt Name / Version
- Exact Evaluation Result
- Judge Decision Category
- Rationale
- Uncertainty / Limitations
- Human Review Required: Yes / No

---

## 8. AI Judge Decision Categories

AI judge output must use categorical judgments only:

- **PASS**
- **FAIL**
- **NEEDS_HUMAN_REVIEW**
- **OUT_OF_SCOPE**
- **TESTS_INSUFFICIENT**
- **SECURITY_RISK**

Do **not** use uncalibrated percentage scores (e.g. 87/100, 92%) as a passing
condition. Such scores are pseudo-precision and are not a reliable gate.

---

## 9. Known AI Judge Risks

Known risks to account for when interpreting AI judge output:

- self-bias
- position bias
- verbosity bias
- inconsistency
- overconfidence
- missing context
- prompt drift
- model/version drift
- weak tests creating false confidence

These risks are why an AI judge can only ever be supporting evidence.

---

## 10. Risk-Based Evaluation

Evaluation requirements scale with risk level:

| Risk Level | Evaluation Requirements |
|------------|-------------------------|
| **readonly** | Must not modify files. |
| **low** | Applicable exact checks; AI judge may assist. |
| **medium** | Explicit functional verification, or a documented reason why exact testing is not possible; diff review required. |
| **high** | Exact evaluation + independent human review; AI judge may assist only. |
| **milestone** | Consider multi-tool / multi-model review + human confirmation + stronger regression evidence. |

Higher-risk work always requires stronger verification.

## 11. Model / Tool Comparison

When comparing different models or tools, keep the evaluation conditions
consistent:

- same task
- same project state / context
- same allowed files
- same forbidden files
- same acceptance criteria
- same test commands
- same review checklist
- same retry budget

Record for each comparison:

- tool
- model
- model/version (if available)
- execution result
- exact evaluation result

Comparison based on "which one feels smarter" is not permitted.

---

## 12. Automation Authority Principle

The higher the automation authority, the stronger the evaluation requirements:

```
read-only analysis
<
controlled file editing
<
command execution
<
external agent execution
<
push / deployment / production actions
```

Higher-authority operations must **not** lower evaluation standards simply
because the agent is perceived as more capable.

## 14. Forbidden Practices

The following practices are forbidden:

- Treating "AI says done" as automatically verified
- Reading only the completion report without checking the diff
- Claiming "fully verified" when applicable tests or required exact checks were not run and no reason for non-applicability was recorded (documentation and readonly tasks may have no applicable tests)
- Letting an AI judge PASS override a failed required exact evaluation or required deterministic gate
- Using AI judge percentage pseudo-precision (e.g. 87/100) as a gate
- Not recording the judge model / prompt version
- Relying only on an AI judge for high-risk tasks
- Comparing different models using different task conditions and treating the results as equivalent
- Increasing automation authority without increasing evaluation
- Continuing to rely only on human discovery for failures that can be deterministically checked
