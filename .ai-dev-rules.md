## 1. SOP v2 General Principles

- **Plan first, then act** — Always analyze, plan, and confirm the approach before writing code.
- **Small tasks, no big rewrites** — Break work into small, focused changes. Do not undertake large refactors unless explicitly tasked.
- **Explicit allowed scope** — Clearly define which files may be modified before starting.
- **Explicit forbidden scope** — Clearly define which files must NOT be modified.
- **Applicable exact checks must pass before suggesting a commit** — Never recommend a commit when a required evaluation gate fails. Documentation / `readonly` tasks may have no applicable tests; record non-applicability per [`EVALUATION_POLICY.md`](EVALUATION_POLICY.md).
- **High-risk tasks require human confirmation** — Never auto-execute high-risk changes.
- **No automatic `git push`** — Pushing requires explicit human approval.
- **No automatic `git merge main`** — Merging requires explicit human approval.
- **Do not modify `.env`, secrets, tokens, API keys, or real production config.**
- **Do not let AI decide major architectural directions** — Humans make strategic decisions.
- **Do not perform large-scale refactoring** — Refactor only as instructed and scoped.

### 1.1 Evaluation & Verification

All AI-assisted task verification follows [`EVALUATION_POLICY.md`](EVALUATION_POLICY.md):

- A completion report is **execution evidence only** — it cannot alone mark a result as verified.
- Run **applicable exact checks** (tests, lint, build, deterministic validation) where available.
- `high` / `milestone` tasks require **human review** per risk level.
- Do not duplicate EVALUATION_POLICY content here.

## 2. Risk Levels

| Level       | Description | Auto-Retry Limit | Human Review Required |
|-------------|-------------|------------------|-----------------------|
| `readonly`  | Read-only analysis, documentation review, code explanation | None (no changes) | No |
| `low`       | Bug fix, test update, minor doc change, small config tweak | Up to 2 auto retries | No |
| `medium`    | Scoped feature, moderate refactor, dependency update without security or schema impact | Up to 1 auto retry | No |
| `high`      | Authentication, permissions, DB schema, policy, audit, auto-exec commands, production config, data deletion, payment, privacy data | No auto retry | **Yes — must be confirmed by human before execution** |
| `milestone` | Major release, cross-cutting change, breaking API, security audit | No auto retry | **Yes — requires Codex + Claude/Cursor/ChatGPT full review** |

### Risk Level Guidelines

- **Low** tasks may auto-retry up to 2 times after test failure.
- **Medium** tasks may auto-retry up to 1 time after test failure.
- **High** tasks must stop and wait for human review upon any test failure.
- **Milestone** tasks require a multi-tool review (Codex + Claude/Cursor/ChatGPT) before any commit.

## 4. Standard Development Flow

Follow these steps in order:

1. **`git status`** — Confirm working directory is clean (no uncommitted changes).
2. **Plan task** — Understand requirements, identify files to change, assess risk level.
3. **Assign risk level** — Tag the task as `readonly` / `low` / `medium` / `high` / `milestone`.
4. **Select tools** — Choose appropriate tools based on scope and risk (see §3 Tool Division).
5. **Define allowed & forbidden scope** — List which files may be modified and which must not be touched.
6. **Implement in small steps** — Make one logical change at a time; do not commit unless explicitly instructed.
7. **`git diff` review** — Review every change before committing.
8. **Applicable exact evaluation** — Run applicable exact checks (tests, lint, build, deterministic validation) per [`EVALUATION_POLICY.md`](EVALUATION_POLICY.md). Documentation / `readonly` tasks may have no applicable tests.
9. **Risk-based review & fixes** — Fix exact-check failures within allowed retry limits per risk level.
10. **Human confirm high-risk tasks** — For `high` or `milestone`, stop and wait for human approval (risk-based human review).
11. **Commit** — Use [Conventional Commits](#6-commit-conventions-conventional-commits) format.
12. **Do NOT push automatically** — Pushing requires explicit human instruction.
13. **Do NOT merge main automatically** — Merging requires explicit human instruction.

## 5. Code Quality & Style

### 5.1 General Coding Rules

- **Clarity over cleverness** — Write code that is easy to read and understand.
- **Single Responsibility** — Each function, module, or component should do one thing well.
- **DRY (Don't Repeat Yourself)** — Extract repeated logic into reusable utilities.
- **Fail fast** — Validate inputs early, crash or return clear errors immediately.
- **Defense in depth** — Validate, sanitize, and escape data at every boundary.
- **Small functions** — Prefer functions under 50 lines.
- **Meaningful names** — No abbreviations unless conventional. Use descriptive variable and function names.
- **Focused files** — One primary export per module unless grouping closely related utilities.

### 5.2 Naming Conventions

| Kind              | Convention       | Example                  |
|-------------------|------------------|--------------------------|
| Variables         | `camelCase`      | `userName`               |
| Functions         | `camelCase`      | `fetchUserData()`        |
| Classes           | `PascalCase`     | `UserService`            |
| Constants         | `UPPER_SNAKE`    | `MAX_RETRY_COUNT`        |
| Files/Dirs        | `kebab-case`     | `user-profile.ts`        |
| React Components  | `PascalCase`     | `UserProfile.tsx`        |

## 7. Security

- Never hardcode secrets, tokens, or API keys.
- Use environment variables for configuration.
- Validate and sanitize all user-supplied input.
- Use parameterized queries / ORM to prevent SQL injection.
- Set appropriate CORS, CSP, and HTTP security headers.

## 8. Testing

- Write tests for business logic — aim for > 80% coverage on critical paths.
- Prefer unit tests over integration tests for isolated logic.
- Write at least one integration or E2E test for each key user flow.
- Mock external services in unit tests.
- **Tests must pass before any commit is suggested.**

## 9. Aider Strong Whitelist / AI Tool File Scope Control

> **Purpose**: Prevent Aider and other AI execution tools from modifying files outside the explicitly allowed scope. This is the core gate for risk-graded automated development pipeline.

### 9.1 Allowed Files Must Be Explicitly Listed

- Every AI task that modifies files **must** explicitly list its **Allowed files** or **Allowed directories** before any change begins.
- Modifying any file outside the Allowed scope is **strictly forbidden by default**.
- Creating new files outside the Allowed scope is **strictly forbidden by default**.
- If a task requires new files, their **complete relative paths** must be listed before the task starts.
- The following **broad-authorization patterns are strictly prohibited**:
  - `"modify anything needed"`
  - `"you decide files"`
  - `"fix all related files"`
  - `"fix any issues you find"`
  - Any other phrasing that delegates file selection to the AI.

### 9.2 `Add file to the chat?` Decision Rules (Aider-Specific)

When Aider asks `Add file to the chat?` (or equivalent), the following rules apply:

| Condition | Decision |
|-----------|----------|
| File is clearly relevant **and** within the allowed scope | `Y` (Yes) |
| File is sensitive (secrets, config, `.env`, production config) | `N` (No) |
| File relevance or safety is uncertain | `N` (No) |
| Aider offers `all files` / `auto add` / `don't ask again` | **Never accept** — reject these options immediately |
| Aider asks about adding multiple files at once | Reject the batch; add files one by one if needed |

### 9.3 File Creation Guardrails

- If Aider or any AI tool requests to create a file, the **full file path must be confirmed as a normal project path** before proceeding.
- The following **abnormal file name patterns** indicate the AI has misidentified the task boundary. These must be **rejected** and the task **stopped** for re-planning:
  - File names containing natural language or explanatory text (e.g., `fix-login-bug.js`, `updated-config-file.json`)
  - File names containing `SEARCH/REPLACE`, `Let's`, `Here is`, or similar LLM-patch fragments
  - File names containing patch snippets, markdown fragments, or code blocks
  - File names that look like a conversation response rather than a source file
- If uncertain whether a file should be created, the AI must **ask the user first** and must **not** create it automatically.
- **Do not create `plans/` or implementation plan files** unless the task explicitly allows.

### 9.4 Git Restrictions for AI Tools

- **Automatic `git commit` is forbidden** — No AI tool may commit changes without explicit human instruction.
- **Automatic `git push` is forbidden** — Pushing to any remote requires explicit human approval.
- **Automatic `git merge` is forbidden** — Merging branches requires explicit human approval.
- These restrictions apply to all AI tools including Aider, Zoo Code, and any other execution agent.

### 9.5 High-Risk Task Exclusion

- **High-risk tasks must NOT be delegated to Aider or similar auto-execution tools.**
- High-risk tasks (see §11) require **human review and multi-tool advanced review** before any change is made.
- Aider may only handle **low-risk** and explicitly vetted **medium-risk** tasks with a clear, pre-defined file list.

### 9.6 Enforcement

- If any AI tool attempts to violate these rules (e.g., creates an unauthorized file, modifies out-of-scope code, auto-commits), the task must be **immediately paused** and escalated to a human reviewer.
- The `allowed_files` and `forbidden_files` lists in the task definition take precedence over any tool-suggested scope expansion.
- When in doubt, **stop and ask** rather than proceed with an ambiguous file scope.

## 11. High-Risk Tasks (Require Human Confirmation)

Any change touching these areas is classified as **high** risk:

- **Authentication** — Login, signup, OAuth, session management, JWT, password handling
- **Authorization / Permissions** — RBAC, ACL, role/scope checks, access control
- **Database schema** — Migration, table creation, column changes, index changes, data type changes
- **Policy** — Security policy, compliance policy, terms of service
- **Audit** — Audit log changes, audit trail modifications
- **Auto-executed commands** — Any command that runs automatically with side effects
- **GitHub token / CI tokens** — Any credential used in CI/CD
- **Data deletion** — `DROP`, `DELETE`, `TRUNCATE`, file deletion, data purge
- **Production deployment** — Any change that affects production environments
- **Payment / Investment / Auto-trading** — Financial transaction logic
- **User privacy data** — PII, GDPR-related, user data export/import

> **Rule**: For any high-risk task, the AI must:
> 1. Flag the risk level upfront.
> 2. Present the plan to the human.
> 3. Wait for explicit confirmation before making any changes.
> 4. After implementation, request human review before commit.

## 13. Post-Completion Output Requirements

After completing any task, the AI **must** output the following in its completion message:

1. **Modified files** — List all files that were changed.
2. **Summary of changes** — What was changed in each file.
3. **Tests executed** — Which tests were run.
4. **Test results** — Whether tests passed or failed.
5. **Risk points** — Any remaining risk concerns.
6. **Human review needed?** — Whether the task requires human review.
7. **No `git commit` confirmation** — Confirm that no commit was automatically made.
8. **No `git push` confirmation** — Confirm that no push was automatically made.
9. **No `merge main` confirmation** — Confirm that no merge was automatically performed.
