## 1. General Principles

- **Clarity over cleverness** — Write code that is easy to read and understand.
- **Single Responsibility** — Each function, module, or component should do one thing well.
- **DRY (Don't Repeat Yourself)** — Extract repeated logic into reusable utilities.
- **Fail fast** — Validate inputs early, crash or return clear errors immediately.
- **Defense in depth** — Validate, sanitize, and escape data at every boundary.

## 2. Code Style & Formatting

- Follow the project's existing code style (linter + formatter config).
- Use meaningful variable and function names — no abbreviations unless conventional.
- Keep functions short (< 50 lines preferred).
- Keep file scope focused — one primary export per module unless grouping related utilities.

## 3. AI-Assisted Development Rules

### 3.1 When using Aider

- Provide full context in the prompt — include error messages, stack traces, and relevant file excerpts.
- Review every diff before applying — never accept blindly.
- Use `--map-refresh` or `/add` to include required files explicitly.

### 3.2 When using Cursor / Windsurf / IDE AI

- Use inline chat for small, scoped changes (< 10 lines).
- Use Composer / Agent mode for multi-file features.
- Always review the generated code before saving.

### 3.3 When using Copilot

- Write a clear comment or function signature first, then let Copilot fill the body.
- Verify generated code for correctness — Copilot may hallucinate APIs.

### 3.4 When using Codex (or similar CLI agents)

- Use for large-scale refactors, permission/security reviews, and pre-release audits.
- Always run in dry-run mode first.
- Review the plan before execution.

### 3.5 AI Tool File Creation Safety Rule

- AI tools (including Aider) must not create new files outside the allowed modification scope.
- If the tool requests to create a file, it must first confirm that the file path is a normal project path.
- If the file name or path contains natural language, explanatory text, `SEARCH/REPLACE`, `Let's`, `Here is`, or similar content, the tool must refuse to create the file and stop checking.
- If uncertain whether a file should be created, the tool must ask the user first and must not create it automatically.

```

```

| Type       | Usage                                      |
|------------|--------------------------------------------|
| `feat`     | A new feature                              |

| `chore`    | Tooling, dependencies, CI changes          |
| `docs`     | Documentation only                         |
| `style`    | Formatting (no logic change)               |
| `refactor` | Code change that neither fixes nor adds    |

## 5. Before Submitting a PR

- [ ] Code builds and passes lint (`npm run build && npm run lint` or equivalent).
- [ ] Tests pass (`npm test` or equivalent).
- [ ] No `console.log` / `debugger` left behind (use a proper logger).
- [ ] New files include a minimal doc comment explaining purpose.
- [ ] API / breaking changes are documented.
- [ ] Relevant issue is linked in the PR description.
- [ ] **Do not** include API keys, secrets, or `.env` files.

---

## 6. Security

- Never hardcode secrets, tokens, or API keys.
- Use environment variables for configuration.
- Validate and sanitize all user-supplied input.
- Use parameterized queries / ORM to prevent SQL injection.
- Set appropriate CORS, CSP, and HTTP security headers.

---

## 7. Testing

- Write tests for business logic — aim for > 80% coverage on critical paths.
- Prefer unit tests over integration tests for isolated logic.
- Write at least one integration or E2E test for each key user flow.
- Mock external services in unit tests.
